## v20 — 自動每小時從流程A 同步 `leads.db`，取代純手動上傳

使用者反應 `klub-us-dashboard.zeabur.app/?sort=phone&order=desc` 的數字一直沒動，
問「為什麼數字都沒有動」，並確認希望改成「有資訊進來就自動變動」。

### 成因
這個 dashboard 讀的是**自己本機的一份 `leads.db`**，跟流程A（klub-lead-scheduler）
的正式資料完全是兩份獨立檔案，過去只能靠人工呼叫 `/upload-db` 手動上傳才會更新——
沒有人上傳，畫面就永遠停在上次上傳當下的快照，跟流程A 持續新增/補齊的資料脫節。
這是「三個系統各自一份 DB、互不同步」的架構性問題在 dashboard 這端的表現。

### 改動（`dashboard.py`）
- 新增 `SCHEDULER_DB_URL`（預設指向流程A 的 `/download-db`）與
  `SCHEDULER_DB_PASSWORD` 兩個環境變數。
- 新增 `_refresh_from_scheduler()`：向流程A 的 `/download-db` 要最新的
  `leads.db`，先下載到暫存檔、確認能開啟且 `leads` 表可查詢筆數後，才用
  `shutil.move()` 原子性覆蓋本機 `DB_PATH`（避免下載到一半或壞檔就整份蓋掉，
  在保護原本核准/寄信引用資料完整性）。
- 新增 `_run_scheduler()`：背景 daemon thread，開機時立即跑一次，之後每小時
  `schedule.every().hour.do(...)` 自動重跑，不用手動觸發。
- `SCHEDULER_DB_PASSWORD` 未設定時直接跳過同步並記 log，不影響原本手動
  `/upload-db` 路徑（新增機制、沒有拿掉舊的手動入口）。

### 部署前處理
`_klub-us-dashboard` 這個資料夾裡本來就有一批跟這次改動無關、屬於其他工作階段
留下的未提交異動（`Dockerfile`、`email_tracker/main.py`、`email_sender/us_email_sender.py`、
`us_lead_enricher_step2_v10.py`、舊快照 `leads.db`，以及誤刪的 `zbr.yaml` build
設定檔）。因為 Zeabur 這個服務走本機直傳部署（不是 git 自動部署），會把當下整個
資料夾內容原封不動包上去，所以部署前先用 `git stash` 把這些無關檔案暫存移開，
只留 `dashboard.py` 的改動上線，部署完成後再 `git stash pop` 全部還原，避免這次
順手把不相關、未經檢視的異動（尤其是會影響建置方式的 `zbr.yaml` 刪除）也一起
帶上線。
